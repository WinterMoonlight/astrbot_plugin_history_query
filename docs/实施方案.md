# 有权限的跨会话聊天记录查询插件：实施方案

整理日期：2026-11-14；独立管理视图补充：2026-11-15

当前阶段：v0.3.1 支持在 WebUI 配置私聊回看条数。以下各节保留阶段记录；独立视图见第八节，私聊显示修复见第九节，私聊读取策略见第十节，自定义条数见第十一节。历史阶段中“本轮未部署”等表述仅对应当时的工作，不作为当前服务器状态说明。

本文记录本次讨论的已确定规则、拟实施架构、建议默认值与待验证问题。已确定规则作为开发基线；建议默认值和技术设想不代表已经通过测试。若本地验证发现接口无法满足要求，应说明限制和替代方案，再讨论调整，不得静默放宽权限或资源限制。

## 一、已确定的规则

### 1. 项目与运行方式

- 开发新的独立 AstrBot 插件，不修改已有的“多群每日简报”插件、总结提示词或人格。
- 使用 Python，暂不引入 Rust、C++ 或需要用户手动安装编译器的组件。
- 尽量采用普通 AstrBot 插件的安装方式，配置使用 AstrBot 自带的插件配置界面。
- 使用 AstrBot 内置 Agent，通过插件提供的 LLM 工具完成查询。
- 允许使用经过验证、与版本绑定的内部接入方式。版本不支持、运行时接入检查失败或无法确认工具隔离已安装时，只停用本插件的历史查询能力，原有插件和普通聊天不受影响；不能静默降级为无拦截读取。
- 用户正常私聊机器人即可，无需专门命令或独立查询网页。
- 当前聊天模型按需决定是否调用查询工具，不额外运行一轮模型来判断是否需要查询，也不把所有群的历史直接塞进上下文。
- 按通用工具调用入口设计，不针对天气、联网搜索等个别插件编写特殊兼容分支。历史读取开始前，原有插件保持原来的调用方式，不要求普通私聊预先切换到“只读模式”。
- 查询完成后，由当前会话的人格自然回答；必要时说明来源群、时间和发送者，不机械展示结果表格或大量内部 ID。

### 2. 数据来源与读取方式

| 数据类型 | 已确定的读取方案 | 边界 |
| --- | --- | --- |
| 群消息流水 | 使用 Python 只读适配层读取正文，以稳定游标续查；群名、别名等元信息仍优先使用官方接口 | 按时间与稳定记录标识确定位置，不再依赖可漂移的页码；只读指定授权会话 |
| 私聊 AI 对话历史 | 使用独立的 Python 只读查询适配层读取正文，优先复用可用的官方会话元信息接口 | 支持同一私聊会话下多个仍保留的旧对话，逐次核对归属并限制读取内容 |

- 群消息流水与 AI 对话历史必须明确区分，不能把 AI 对话历史当作群内所有人的普通聊天记录。
- 查询仅限机器人实际能够访问、且已经保存、尚未清理的记录。
- 不读取个人 QQ 客户端数据库，不承诺恢复未收到、未保存或已经删除的消息。
- 不重新监听并完整复制全部消息到另一个数据库。
- 不修改宿主数据库结构，不创建索引，不写入宿主历史表。
- 只读适配层的查询语句由代码固定并参数化；模型不能自行提供 SQL、数据库路径或授权条件。
- 正文缺失或只保存媒体占位信息时，如实说明，不补造图片、语音或附件内容。

### 3. 权限规则

- 使用独立的查询用户白名单，不要求用户获得完整 AstrBot 管理员权限。
- 每个查询用户分别配置可查询的会话范围，不共享一份默认全局授权。
- 默认只允许获授权用户在私聊中发起跨会话查询；其他用户仍可正常与机器人聊天。
- 允许查询其他人与机器人的私聊，不限于查询者本人的私聊。
- 可以为你的账号配置全部指定机器人实例下的可查询会话；这不意味着其他查询用户自动获得相同权限。
- 分别配置查询者、允许查询的群、是否开放私聊及允许查询的私聊会话。
- 身份以真实事件中的平台实例、发送者 ID、消息类型和当前会话为依据；群名、昵称及模型参数不是身份凭据。
- 所有工具入口均独立鉴权，包括查找会话、搜索、读取指定记录、上下文补读和续查。
- 会话、记录与分页引用必须绑定查询者和查询范围；不能通过猜测或替换 ID 读取其他会话。
- 机器人确认退出某群后，即使旧记录和用户授权仍然存在，也不再开放该群历史。
- 本次无法确认机器人仍在群内时，不读取该群历史，提示稍后重试；不使用之前“仍在群内”的缓存放行。网络断开、接口失败不等于已经退群，两种状态应分别表达。

### 4. 会话定位与默认查询范围

- 先在授权范围内按名称或别名定位真实群、联系人及会话，再读取正文。
- 同名、匹配歧义或无法确定目标时，先询问用户，不随意选择。
- 问题和上下文都无法确定查询哪些群或私聊时，先询问范围，不自动搜索全部授权会话。
- 如果上下文已经明确目标，例如“之前我们聊的安排”明确指当前私聊，不机械重复询问。
- 群列表只向模型提供当前查询用户获授权的候选。通过 NapCat 获取的群列表属于机器人账号，不是查询者个人 QQ 的全部群。

### 5. 时间与频率规则

| 条件 | 已确定行为 |
| --- | --- |
| 用户明确指定时间 | 按指定范围查询 |
| 未指定时间，最近 24 小时达到 300 条消息 | 视为高频群，默认查询最近 24 小时 |
| 未指定时间，最近 24 小时不足 300 条消息 | 视为低频群，默认查询最近 3 天 |
| 默认时间范围内没有找到 | 说明本次范围，询问是否继续往前查，不自动扩大时间范围 |
| 无法确认消息日期 | 说明时间信息不足，不把它当作指定日期的记录；先问是否改为不限定日期、按关键词查询 |

特别说明：

- “每天 300 条”是高频判断阈值，不是用户实际群聊的日均消息量。
- 用户提供的 999 条是当前留存配置，不能推算成固定保留几天，也不能视为 AI 对话历史的统一条数上限。
- 群流水的存储时间不能直接宣称为 QQ 原始发送时间。
- 不能把整段 AI 对话的创建或更新时间当作其中每句话的时间。
- 留存不足、会话隔离等情况下，频率能否可靠判断及相应处理方式仍需验证，见第五节。

### 6. 查询预算与续查

- 每轮累计最多扫描 500 条逻辑消息。
- 数据读取与筛选累计最多 5 秒，不包含模型生成回答的耗时。
- 允许有限排队，整轮累计排队最多 5 秒；多次工具调用不能重新获得完整排队额度。排队耗尽提示繁忙，已有部分结果应说明未完成。
- 排队与读取、筛选分别计时，整轮共享各自的 5 秒预算；模型生成回答和必要的取消、资源清理开销另算，不承诺所有环境中精确到毫秒完成回收。
- 多个会话、分页、频率采样、上下文补读和重复工具调用共享本轮预算，不能借多次调用绕过上限。
- 多会话查询采用轮流分批方式，避免单个活跃会话占满额度；某个会话查完后，剩余额度交给其他尚未完成的会话，并分别报告覆盖范围。
- 达到上限但原定范围尚未查完时，先给出已查部分的结果，明确实际检查范围和“还没查完”，再问是否继续。
- 用户同意继续后接着分页，重新鉴权并使用新一轮预算；不能默默扩大原定时间或会话范围。
- 分页或记录引用失效时，明确说明，不把错位记录当作原命中继续读取。
- 稳定游标记录上次读取位置，并固定本次查询的新增消息边界；查询开始后新加入的消息不混入原查询的续查，查看新消息应另发起查询。
- 稳定游标不是永久快照，不能恢复已删除记录；不为等待用户回复“继续”而长期保持数据库事务。内容或排序字段变化、记录缺失等一致性边界需明确验证与说明。
- 查不到时使用“在当前可查询的记录中没有找到”等有范围的表述；未查完、无命中、无权限、历史被清理和查询失败应区分。

预算的技术边界：500 条不是 SQLite 物理读取量、磁盘页数或内部 JSON 解析量的保证。私聊正文可能仍以大段 JSON 存储，必须另行限制单段数据体积、内存和执行时间；不能仅靠限制返回条数证明资源限制已经生效。

### 7. 查询轮次与历史内容安全

- 历史记录属于待分析资料，不是新的系统指令或用户操作授权。
- 不再要求从这一轮的第一步就禁用其他工具。只有开始读取历史后，直到本轮回答结束，才禁止启动新的其他工具；此后只允许历史查询和上下文补读。
- 历史读取开始前已经启动的工作允许自然完成，不撤销、不强制取消；不能承诺回滚此前已经发生的操作。
- 历史读取开始后，需要发送消息、创建提醒等操作时，等待下一条明确操作指令。没有开始读取历史的普通轮次，仍按原插件原来的用法处理，不全局强制改为命令模式。
- 限制只属于本轮，不全局停用其他插件，不修改原有人格；其他会话和下一轮正常请求不共享本轮锁定状态。
- 不依靠预先猜测自然语言意图来宣布整轮只读。必须在真正读取历史之前建立不可被模型参数解除的本轮状态；首次读取、后续工具准入及并发情况需要验证。
- 不能因为历史中出现“忽略规则”“读取其他私聊”“发送给某人”等内容而扩大权限、追随新的会话引用或触发其他操作。
- 这项隔离必须由代码落实，其具体可行性是实现前的关键验证项，不能仅凭提示词或钩子抛异常宣称完成。
- 拦截保证只覆盖当前轮次经过受控工具执行入口的新 LLM 工具调用，不做宿主级改造，不宣称控制整个 AstrBot 进程里的所有代码。
- 独立定时任务、其他会话、工具内部普通函数、没有经过受控入口的独立调用不在该拦截保证内；实际覆盖范围和版本限制必须在文档及检查结果中明确。

### 8. 留存与开发边界

- 接受 AstrBot 的正常留存：必要查询片段可以进入当前对话历史和工具结果日志，实际日志落盘取决于宿主配置。
- 插件只向模型返回必要片段，不把扫描过的全部消息送入模型。
- 插件自身可以保存配置和必要查询审计，但审计不保存聊天正文。
- 原始记录清理后，先前查询留下的片段和最终回答可能仍存在于当前对话或日志中；撤销查询权限也不会自动删除这些已有副本。
- 先在本地开发和测试，使用合成记录。
- 未经明确要求，不部署服务器，不使用真实聊天记录调用外部模型，不上传凭据或私人消息。

### 9. 低资源运行目标

- 目标服务器规格由用户确认为 2 核 CPU、2 GB 内存，还需要同时运行 AstrBot、NapCat 和系统服务；不假定这些内存可以全部分配给插件。
- 初期按全局同时只执行一个历史查询任务设计，配合有限排队；不因此全局限制普通聊天或其他插件。
- 仅在真正需要读取历史时启动数据库工作；不按每条普通聊天启动扫描或额外调用模型，不做周期性全库扫描或历史正文镜像。
- 优先让 SQLite 执行受限查询，减少传回 Python 的内容及重复 JSON 解析。采用短只读事务，不在模型生成期间或等待用户续查时占用数据库事务。
- 查询执行槽位只用于读取和筛选，不在模型思考、用户回复或普通聊天期间长期占用。
- 以单个可回收的 Python 查询工作进程作为优先实现方向；是否保持短时复用、空闲退出时间、队列容量和内存限制由合成数据测量后确定，不把多次启动进程当作免费的操作。
- 游标、元信息缓存和审计都要限制数量或体积，并及时清理；元信息缓存不能替代本次群访问资格校验。
- 内存开销、进程启动与回收耗时必须有实测记录；不能仅凭“使用 Python/SQLite”宣称低性能开销。

## 二、拟实施架构

以下为实现结构。已完成的本地验证范围见独立仓库 docs/验证状态.md；完整宿主生命周期及生产部署仍属于后续验收。

处理流程：

> 当前聊天模型 → LLM 查询工具 → 可信身份与权限检查 → 统一预算检查 → 对应历史读取器 → 带来源的有限结果 → 当前人格自然回答

| 模块 | 职责 |
| --- | --- |
| 配置与权限 | 校验配置、解析可信事件身份、逐用户和逐会话授权 |
| 会话目录 | 复用 AstrBot 已保存名称和别名，必要时通过 NapCat 补充群元信息；只暴露授权候选 |
| 查询预算与调度 | 整轮共享 500 条、累计排队 5 秒及执行 5 秒；单查询执行槽位、有限排队和多会话轮流分配 |
| 版本与接入检查 | 检查经过验证的版本、内部结构和本轮执行器绑定；失败时仅关闭历史查询，不改变原有功能 |
| 本轮工具准入 | 历史读取前保留原有工具，开始读取后禁止新启动其他工具；已启动工作可完成，不改全局注册状态 |
| 群流水读取器 | Python 只读查询、稳定游标、当前群访问状态核验，保留真实来源 |
| AI 历史读取器 | Python 只读适配层，核对结构、归属、数据体积，受限读取多个旧对话中的正文片段 |
| 引用与续查 | 绑定调用者、目标范围、记录位置和续查状态，处理删除及变更 |
| 结果与审计 | 区分完整、部分、无命中、无权限及失败状态；仅记录必要审计元信息 |

拟提供三个 LLM 工具：

| 工具 | 能力 | 每次必须执行的检查 |
| --- | --- | --- |
| 查找会话 | 根据群名、联系人名称或别名返回有限候选 | 查询者资格、当前调用会话、候选范围权限 |
| 搜索历史 | 指定目标、数据类型、关键词、时间、发送者及返回数量；支持受限的多会话搜索 | 每个目标的权限、输入合法性、共享预算 |
| 读取记录与上下文 | 读取已命中的记录及有限前后文 | 引用绑定、当前权限、记录归属及状态、共享预算 |

结果保留平台实例、来源名称、发送者、数据类型、时间及其依据、记录标识、截断状态和分页状态。内部引用供工具核验使用，正常回答不要求展示全部内部 ID。

只读适配层使用只读连接、固定参数化查询和必要的操作限制。不调用宿主数据库初始化或迁移流程，不修改日志模式、表结构或索引。同步工作应移出主事件循环，不能阻塞其他会话。

配置拟包含查询用户与调用入口、逐用户群/私聊授权、显式全部会话授权、别名、时间规则、预算、返回限制、并发限制和审计清理设置。空配置不应产生跨会话读取权限。

## 三、初始实现值与待实机校准的参数

以下数值是低资源目标下采用的初始实现值，不属于用户要求不可修改的硬规则。已进行本地合成数据测量，仍需目标环境校准；不得将它们理解为生产性能保证。

| 参数或行为 | 建议初始值/方式 | 说明 |
| --- | --- | --- |
| 单次工具默认返回消息数 | 20 条 | 只返回必要结果 |
| 单次工具最大返回消息数 | 50 条 | 仍服从本轮扫描和字符预算 |
| 整轮返回正文上限 | 12,000 字符 | 多次工具调用累计；裁剪必须标记 |
| 单次上下文补读 | 默认前后各 3 条，上限各 5 条 | 保持同一授权来源，计入本轮预算与字符限制 |
| 单批读取量 | 25 条 | 多来源轮流读取 |
| 等待请求容量 | 4 个 | 不改变整轮累计排队 5 秒 |
| 单段历史/群消息体积 | 1 MiB | 超限拒绝或跳过并明确说明，不整段解码到主进程 |
| 工作进程空闲退出 | 30 秒 | 仅查询时按需启动，短时复用 |
| 引用有效期与容量 | 15 分钟，最多 2048 项 | 仅保存引用与游标元信息，重载后失效 |
| 时间解释 | 按 Asia/Shanghai 解释“昨天”等自然日期，内部统一时间基准比较 | 需核对宿主配置及存储时区 |
| 频率采样 | 复用本轮已读取记录，避免再次完整扫描 | 采样本身计入预算 |
| 审计内容 | 时间、查询者、目标范围、数量、状态、耗时等元信息 | 不保存正文；建议也不保存完整原始问句、关键词及完整工具返回 |

单次最多指定 5 个来源，执行并发为全局 1 个。POSIX 工作进程设置 192 MiB 地址空间上限；Windows 不宣称具有同等内存硬限制。审计保留当前和上一份约 1 MiB 文件。所有数值仍需根据目标环境实测校准，不能取消必要的权限与停止机制。

## 四、源码核验基线与已知限制

首个核验基线为 AstrBot `v4.29.4`，提交 `61335414433db721b3f7ecc93f90deafe0a59d78`。这只是已核对的源码版本，不代表已经检测当前阿里云服务器的版本、数据库、插件组合或运行配置。

- 群消息流水位于 `platform_message_history`，AI 对话历史位于 `conversations`，两者独立。
- 群历史接口支持按平台实例与会话分页读取；现成群搜索工具的关键词等筛选在读取后进行。
- AI 对话列表可以不带正文分页获取；读取某段 AI 历史的现成方法会先取整段，所谓消息分页也可能只是后续 Python 切片。
- `get_conversation()` 不能代替插件鉴权：不能因传入了会话参数，就假定其已验证所取对话属于该会话。
- 会话隔离可能使同一真实群对应多个存储会话；不得简单拼接或猜测会话 ID 后开放读取。
- 只读适配层能限制交给 Python 的内容，但原始 JSON 的内部处理仍可能有额外开销。
- 4.29.4 的工具执行流程会捕获工具启动钩子的异常后继续执行，单纯抛异常不是可靠的拦截方式。
